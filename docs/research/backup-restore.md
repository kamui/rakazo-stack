## Answer

- **Rakazo ships a backup and restore procedure, but not for the published-images compose.** Its production script takes a live custom-format `pg_dump` and a live `tar` of the volume mounted at `/data`. The restore steps are documented by hand. Nothing is written for `docker-compose.images.yml`, so the stack adapts them.
- **Back up two things:** a `pg_dump` per database (Rakazo, Honcho) and a tar of `appdata`. `webassets`, all `lemonade-*` volumes, `honcho-tiktoken` and the `tar` staging/cache directories can be rebuilt. `tailscale-state` is optional and needs care.
- **Keys that must travel with the data:** `ENCRYPTION_KEY` (and `ENCRYPTION_MASTER_KEYS` if set), `BETTER_AUTH_SECRET`, and Honcho's `AUTH_JWT_SECRET`, unless the Honcho admin JWT stored in Rakazo is reminted. Safe to regenerate on a fresh machine: `POSTGRES_PASSWORD`, `POSTGRES_APP_PASSWORD`, `HONCHO_DB_PASSWORD`, `SCREEN_PROXY_SECRET`, `SANDBOX_SUPERVISOR_TOKEN`, `LEMONADE_API_KEY`.
- **Restore order:** start the empty Postgres, create the `rakazo_app` role, then run `pg_restore`. Swap the `appdata` tree in, then start everything; `migrate` sets the app login's password from the new env. Restore Honcho's dump before Honcho's API starts.
- **Bot homes in `appdata` are plaintext.** Only artifacts and database content are encrypted. The archive holds logged-in browser profiles and CLI tokens, so treat it as secret.
- **Bot computers are rebuilt on demand.** Their container layers and per-bot networks are disposable. They aren't Compose services, though: `docker compose stop` leaves them running.
- **A new Instance URL** costs sign-ins and passkeys. MCP servers connected with OAuth and Slack installs may also need reconnecting. Message links refer to files by id, not by URL.

## 1. Rakazo upstream backup guidance

- Rakazo ships `docs/self-host-backups.md`, `infra/compose/backup-prod.sh` and `backup-drill.sh`, plus source-checkout `scripts/backup.sh` and `restore.sh`. `docs/self-host-storage.md` covers keys and homes, not procedure. None targets `docker-compose.images.yml` or `install-images.sh`.
- **Production (`backup-prod.sh`), live, nothing stopped:**
  - DB: `pg_dump --format=custom --no-owner --no-privileges -U "$POSTGRES_USER" "$POSTGRES_DB"` through `compose exec -T postgres`, verified with `pg_restore --list` while it streams ([R/infra/compose/backup-prod.sh#L165-L172](https://github.com/elie222/rakazo/blob/v0.4.0/infra/compose/backup-prod.sh#L165-L172)).
  - Files: `tar -czf - --numeric-owner -C <appdata mountpoint> .`, run on the host, not through `exec api`. Upstream's reason: "the cap-dropped api user cannot read the root-owned mode-600 bot homes". The volume is found by inspecting the running api's `/data` mount ([#L66-L76](https://github.com/elie222/rakazo/blob/v0.4.0/infra/compose/backup-prod.sh#L66-L76), [#L173](https://github.com/elie222/rakazo/blob/v0.4.0/infra/compose/backup-prod.sh#L173)).
  - "Bots write while this runs." GNU tar exit 1 ("file changed as we read it") is accepted; only exit 2 fails ([#L208-L216](https://github.com/elie222/rakazo/blob/v0.4.0/infra/compose/backup-prod.sh#L208-L216)).
  - Optional `age` encryption to public recipients, `rclone` off-site copies, and retention ([R/docs/self-host-backups.md#L50-L128](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-backups.md#L50-L128)).
- **Production restore (manual, documented):**
  - Stop `api worker web` and take a rollback `pg_dump -Fc`.
  - Extract `appdata.tgz` with `--numeric-owner` into a clean sibling directory of the volume's data dir.
  - `pg_restore --clean --if-exists --no-owner --exit-on-error --single-transaction`.
  - `mv` the old tree aside and the staged tree in, then `up -d --force-recreate --wait` ([#L142-L182](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-backups.md#L142-L182)).
  - "**Never extract appdata over the active volume.** Files created after the snapshot would survive and mix with the restored database" ([#L142-L146](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-backups.md#L142-L146)).
  - Into a new stack: "create the `rakazo_app` role before the procedure … Do not run the migrations first: tables newer than the snapshot would block the restore" ([#L209-L217](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-backups.md#L209-L217)).
- **Source checkout:** plain `pg_dump -U rakazo rakazo > rakazo.sql` plus `tar -czf homes.tgz data` ([R/scripts/backup.sh#L25-L31](https://github.com/elie222/rakazo/blob/v0.4.0/scripts/backup.sh#L25-L31)). Restore stops `api worker supervisor`, creates `rakazo_app NOLOGIN` if missing, and runs `psql --single-transaction`, then swaps `data/` ([R/scripts/restore.sh#L52-L74](https://github.com/elie222/rakazo/blob/v0.4.0/scripts/restore.sh#L52-L74)).
- Upstream uses `pg_dump`, never `pg_dumpall`; `pg_dumpall` appears only in the Postgres upgrade check ([R/docs/self-host-upgrading.md#L87](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-upgrading.md#L87)). Dump as the owner, since "the app login would only dump rows it is allowed to see" ([R/docs/self-host-configuration.md#L111](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-configuration.md#L111)).
- Point-in-time recovery (WAL to S3) needs the production compose with Postgres 18, so it does not apply here ([#L219-L225](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-backups.md#L219-L225)).
- **Settings → Export/Import data** moves Spaces between installs. It leaves credentials and connections behind, has a 4 GiB cap, and drops files over 8 MiB. It suits moving an account, not backing up an Instance ([#L310-L319](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-backups.md#L310-L319)).

- No separate uploads or attachments tree exists; attachments are artifacts. Those are every subdirectory joined onto `DATA_DIR` in `apps/` and `packages/` outside tests, from a grep of the tag.
- `webassets` (web container) holds "recent builds' hashed assets, so tabs still running one keep loading chunks after a deploy" ([R/infra/compose/docker-compose.images.yml#L524-L526](https://github.com/elie222/rakazo/blob/v0.4.0/infra/compose/docker-compose.images.yml#L523-L526)). It is a cache.
- Size bounds only: a home over 5 GiB or a million files is not saved ([self-host-storage.md#L124-L130](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-storage.md#L124-L130)). Uploads default to 10 MiB per file ([#L207-L208](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-storage.md#L207-L208)). No typical size for a light single-user Instance is stated anywhere (**unverified**; measure on a reference install). A Chrome profile per bot is likely the bulk.
- Upstream's own save path excludes rebuildable caches: `.cache`, `.npm`, `.pnpm-store`, `.yarn/cache`, `node_modules`, `.venv`, `__pycache__`, `.next`, `.turbo`, `*.log`, core dumps and browser caches ([R/docs/computer-runtime.md#L98](https://github.com/elie222/rakazo/blob/v0.4.0/docs/computer-runtime.md#L98)). `backup-prod.sh` does **not** apply these exclusions to its tar. Excluding them is an option for the stack.

## 3. Bot computers' other state

- A container is created with the home as its only persistent mount: a volume subpath of the `/data` volume, plus optional operator host mounts (`SANDBOX_COMPUTER_MOUNTS`). It has `AutoRemove: false` and labels `rakazo.managed`, `rakazo.botId` and `rakazo.spaceId` ([R/infra/sandboxes/supervisor/src/computer-spec.ts#L587-L622](https://github.com/elie222/rakazo/blob/v0.4.0/infra/sandboxes/supervisor/src/computer-spec.ts#L587-L622)). No named volumes of its own.
- The writable layer is disposable: "The disposable OS image is not a portable disk snapshot. System packages installed outside the workspace are lost" ([R/docs/computer-runtime.md#L100](https://github.com/elie222/rakazo/blob/v0.4.0/docs/computer-runtime.md#L100)). Tool caches sit under `/tmp/rakazo-cache`, outside the home ([self-host-storage.md#L131](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-storage.md#L131)). The supervisor also replaces a container whenever its image, user, DNS or mounts change ([R/infra/sandboxes/supervisor/src/index.ts#L284-L301](https://github.com/elie222/rakazo/blob/v0.4.0/infra/sandboxes/supervisor/src/index.ts#L284-L301)).
- **Per-bot networks** (`rakazo-computer-<id>-<hash>`) carry a `rakazo.computerOwner` label hashed from the `/data` volume's name ([computer-spec.ts#L430-L454](https://github.com/elie222/rakazo/blob/v0.4.0/infra/sandboxes/supervisor/src/computer-spec.ts#L430-L454)). They are created when missing ([index.ts#L349-L351](https://github.com/elie222/rakazo/blob/v0.4.0/infra/sandboxes/supervisor/src/index.ts#L349-L351)). Keep the project name `rakazo-stack` so the volume (and owner label) is `rakazo-stack_appdata`.
- **Created on demand after a restore:** the ensure-computer path looks up a container by its `rakazo.botId` label. With none found, it checks the home is writable by `1000:1000`, creates the network and container, and starts it ([index.ts#L231-L370](https://github.com/elie222/rakazo/blob/v0.4.0/infra/sandboxes/supervisor/src/index.ts#L231-L370), [#L1256-L1268](https://github.com/elie222/rakazo/blob/v0.4.0/infra/sandboxes/supervisor/src/index.ts#L1256-L1268)). For remote providers the stored `providerRef` "is an acceleration path, not durable data" ([computer-runtime.md#L82](https://github.com/elie222/rakazo/blob/v0.4.0/docs/computer-runtime.md#L82)). Not exercised: what the UI shows for a computer whose DB row says running until its first ensure (**unverified**).
- Computers are not Compose services, so `docker compose stop`/`down` does not stop them. To quiesce: `docker ps -q --filter label=rakazo.managed=true`. That label is not install-specific; there is no project label on computers.
- Native binaries installed into a home (for example `~/.local`) by an x86-64 computer won't run on an arm64 Mac and vice versa (**unverified** in practice; follows from the homes being plain files).

| Secret | Must match restored data? | Source |
|---|---|---|
| `ENCRYPTION_KEY` | **Yes.** Encrypts stored credentials and derives the default content master key, which wraps `space_keys`. "Without them, a backup of the database and `DATA_DIR` cannot be read." | [R/docs/self-host-storage.md#L20-L28](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-storage.md#L20-L28), [R/docs/self-host-secrets.md#L64-L72](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-secrets.md#L64-L72) |
| `ENCRYPTION_MASTER_KEYS` | Yes, if ever set (empty by default in the stack). | [R/docs/content-encryption.md](https://github.com/elie222/rakazo/blob/v0.4.0/docs/content-encryption.md) ("Master keys") |
| `CONTENT_ENCRYPTION` | Not a key. With `on` (the default for compose), artifact files and message/memory columns are AES-256-GCM under per-space keys wrapped by the master key. Local homes are not encrypted. `off` still reads old ciphertext. | [content-encryption.md#L8-L17](https://github.com/elie222/rakazo/blob/v0.4.0/docs/content-encryption.md#L8-L17), [R/infra/compose/docker-compose.images.yml#L31](https://github.com/elie222/rakazo/blob/v0.4.0/infra/compose/docker-compose.images.yml#L31) |

| `SANDBOX_SUPERVISOR_TOKEN` | No. "API ↔ sandbox supervisor auth"; per-computer control tokens are fresh `randomUUID()`s. | [self-host-secrets.md#L20](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-secrets.md#L20), [index.ts#L369](https://github.com/elie222/rakazo/blob/v0.4.0/infra/sandboxes/supervisor/src/index.ts#L369) |
| `POSTGRES_PASSWORD` | Into a **fresh** volume: no, a dump holds no roles. | `POSTGRES_APP_PASSWORD` | No. `migrate` (run before api/worker on every `up`) creates or alters the `rakazo_app` login with the env password. - The `rakazo_app` role must exist **before** `pg_restore`. The dump carries the job-queue policy `TO rakazo_app` (and grants, without `--no-privileges`). Create it `NOLOGIN`; `migrate` turns it into the login afterwards ([R/docs/self-host-backups.md#L209-L217](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-backups.md#L209-L217), [database-access.ts#L214-L249](https://github.com/elie222/rakazo/blob/v0.4.0/packages/db/src/database-access.ts#L214-L249)).
- If the app password changes without `migrate`, background work stalls with the warning "DATABASE_URL's password changed since `pnpm db:migrate` last ran" ([database-access.ts#L289-L291](https://github.com/elie222/rakazo/blob/v0.4.0/packages/db/src/database-access.ts#L289-L291)). Compose always runs `migrate` first ([R/infra/compose/docker-compose.images.yml#L365-L386](https://github.com/elie222/rakazo/blob/v0.4.0/infra/compose/docker-compose.images.yml#L365-L386)).
- Upstream's rule of thumb: "Moving hosts: copy `.env` and volumes together" and "Recreating random secrets on a volume that still holds Postgres data will desynchronize passwords and encryption" ([self-host-secrets.md#L116-L119](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-secrets.md#L116-L119)).
- Layer secrets: `HONCHO_AUTH_JWT_SECRET` (see Q7). `LEMONADE_API_KEY` and `HONCHO_DB_PASSWORD` can be regenerated on a fresh machine. `TS_AUTHKEY` is single-use input.

## 5. Instance URL baked into data

- **Passkeys:** RP ID is the `WEB_ORIGIN` host. Loopback maps to `localhost`, and plain-HTTP non-loopback hosts get no passkeys ([R/packages/auth/src/passkey.ts#L15-L39](https://github.com/elie222/rakazo/blob/v0.4.0/packages/auth/src/passkey.ts#L15-L39)). Stored passkeys stop working under another host.
- **Sessions:** cookies are scoped to the origin, so a new URL means signing in again. Session rows themselves are not URL-bound (Better Auth DB sessions; not traced further).
- **MCP servers connected with OAuth:** the redirect is always `WEB_ORIGIN/mcp/oauth/callback` ([R/apps/api/src/routes/mcp.ts#L902-L911](https://github.com/elie222/rakazo/blob/v0.4.0/apps/api/src/routes/mcp.ts#L902-L911)). Rakazo stores the dynamically registered client and its `redirectUri` in the encrypted connection material ([R/packages/adapters/src/mcp-oauth.ts#L376-L398](https://github.com/elie222/rakazo/blob/v0.4.0/packages/adapters/src/mcp-oauth.ts#L376-L398)). Token refresh needs no redirect. A new authorization would reuse a client registered for the old URL, and no re-registration on URL change was found, so the provider may reject it until the server is removed and re-added (**unverified**, not exercised).
- **Composio / Pipedream connections:** `redirectUrl` is `${webOrigin}/integrations/callback`, passed only when connecting ([R/apps/api/src/routes/connections.ts#L335](https://github.com/elie222/rakazo/blob/v0.4.0/apps/api/src/routes/connections.ts#L335)). Existing connections are server-side and should survive. New connects use the new URL.
- **Messaging:** webhook URLs live in each provider's console, pointing at `API_URL`. The Slack install redirect comes from `apiUrl` ([R/packages/adapters/src/messaging-composition.ts#L40](https://github.com/elie222/rakazo/blob/v0.4.0/packages/adapters/src/messaging-composition.ts#L40)). The stack doesn't enable these in v1, but any configured webhook needs updating.
- **Files and messages:** message blocks keep `artifactId`, not URLs ([content-encryption.md#L55-L60](https://github.com/elie222/rakazo/blob/v0.4.0/docs/content-encryption.md#L55-L60)). No absolute URLs built from `WEB_ORIGIN`/`API_URL` are stored in rows, apart from the MCP redirect above. Basis: a grep of `new URL(…, webOrigin|apiUrl|authUrl)` in `apps/api`, `apps/worker` and `packages/adapters`.
- **Clients:** the phone app keeps the server URL on the device, so it must be repointed (client-side, not in the backup).

## 6. Consistency

- `pg_dump` "makes consistent backups even if the database is being used concurrently" and "does not block other users" ([PG16 pg_dump.sgml#L39-L43](https://github.com/postgres/postgres/blob/REL_16_0/doc/src/sgml/ref/pg_dump.sgml#L39-L43)). Upstream dumps live. PG18's page adds "pg_dump is generally not the right choice for taking regular backups of production databases" ([PG18 #L44-L48](https://github.com/postgres/postgres/blob/REL_18_0/doc/src/sgml/ref/pg_dump.sgml#L44-L48)), which is about scale and PITR, not correctness.
- Copying `appdata` live: upstream does it and accepts "file changed as we read it" (Q1). Docker computers "work directly in their copy until their next save" ([self-host-storage.md#L118-L122](https://github.com/elie222/rakazo/blob/v0.4.0/docs/self-host-storage.md#L118-L122)). A live tar can catch a browser profile or a half-written home mid-change. For remote computers, upstream quiesces browsers first "so profile databases and login state are copied consistently" ([computer-runtime.md#L98](https://github.com/elie222/rakazo/blob/v0.4.0/docs/computer-runtime.md#L98)).
  - For a clean snapshot, stop `api worker supervisor` **and** the bot computers before the tar (Q3).
  - A live tar is "safe enough" by upstream's standard; the worst case is a torn file inside a home.
- **Row ↔ file coupling:**
  - `artifacts` rows ↔ `artifacts/<space>/<id>`; `space_keys` rows decrypt those files.
  - `computers` rows (home key, revision) ↔ `homes/<key>` + `home-revisions/<key>.txt`.
  - **Dump first, then tar** (upstream order). Every row in the dump then has its file, unless deleted in between. Extra files from after the dump are inert: without object storage the worker only sweeps `staging/`, with no orphan sweep of local homes ([R/packages/adapters/src/home-object-store.ts#L666-L690](https://github.com/elie222/rakazo/blob/v0.4.0/packages/adapters/src/home-object-store.ts#L666-L690)).
  - On restore, replace the tree; never merge it into the live one (Q1).

## 7. Honcho v3.5.0

- **Durable state is all in Postgres:** workspaces, peers, sessions, messages, `message_embeddings`/documents (pgvector columns), the `queue` and `active_queue_sessions` tables, and webhooks ([H/src/models.py#L104-L775](https://github.com/plastic-labs/honcho/blob/v3.5.0/src/models.py#L104-L775)). `VECTOR_STORE_TYPE` defaults to `pgvector`; LanceDB and others need opt-in ([H/src/config.py#L1546](https://github.com/plastic-labs/honcho/blob/v3.5.0/src/config.py#L1546)). Redis is off (`CACHE_ENABLED=false`). `honcho-tiktoken` is a tokenizer cache. Tables live in schema `public` ([config.py#L739](https://github.com/plastic-labs/honcho/blob/v3.5.0/src/config.py#L739)).
- **`AUTH_JWT_SECRET`:** every request JWT is checked with HS256 against it ([H/src/security.py#L134-L146](https://github.com/plastic-labs/honcho/blob/v3.5.0/src/security.py#L134-L146)). Honcho stores no JWTs, but Rakazo stores the admin JWT in its per-Space memory setting (`research/honcho-needs`). Restore the secret, or mint a new admin JWT and update every Space's Honcho setting.
- **Restoring into a fresh `pgvector/pgvector:pg18`:**
  - `POSTGRES_USER=honcho` is a superuser created from env, so the role needs no step and the password can be new.
  - The prototype's `init.sql` creates `vector`, `pg_trgm` and `btree_gin`, and pg_dump emits `CREATE EXTENSION IF NOT EXISTS`, so there is no conflict ([PG18 pg_dump.c#L11773](https://github.com/postgres/postgres/blob/REL_18_0/src/bin/pg_dump/pg_dump.c#L11773)).
  - The extension is created at the target image's pgvector version. The `pg18` tag moves; pin by digest (`research/upstream-upgrades`).
  - **Restore before starting `honcho`.** Its entrypoint runs Alembic `upgrade head` on every start ([H/docker/entrypoint.sh](https://github.com/plastic-labs/honcho/blob/v3.5.0/docker/entrypoint.sh), [H/migrations/env.py#L142-L160](https://github.com/plastic-labs/honcho/blob/v3.5.0/migrations/env.py#L142-L160)). On an empty DB that creates tables the restore then collides with. So run `up -d honcho-db` alone first.
  - Not exercised end to end (**unverified**).
- **Upstream guidance** is a plain `pg_dump … > backup.sql` and `psql` restore ([H/docs/v3/contributing/self-hosting.mdx#L479-L487](https://github.com/plastic-labs/honcho/blob/v3.5.0/docs/v3/contributing/self-hosting.mdx#L479-L487)). Note it uses `exec` without `-T` for the dump (see Q11).
- **No drain needed.** Queue items are rows. A restart cleans up stale work units on the first poll ([H/src/deriver/queue_manager.py#L154-L157](https://github.com/plastic-labs/honcho/blob/v3.5.0/src/deriver/queue_manager.py#L154-L157)), stale after `STALE_SESSION_TIMEOUT_MINUTES=5` ([config.py#L926](https://github.com/plastic-labs/honcho/blob/v3.5.0/src/config.py#L926)). Unprocessed items are re-run after restore, which spends model calls again. Stopping `honcho-deriver` before dumping only avoids capturing in-flight work.

## 9. Tailscale

- State lives in `TS_STATE_DIR`. "The `TS_STATE_DIR` volume ensures the container keeps its identity across restarts. Without it, each restart creates a new node" ([docker-params](https://tailscale.com/docs/features/containers/docker/docker-params)).
- **Restoring `tailscale-state` elsewhere** gives the same node: same key, same 100.x address, same `rakazo` name, and `TS_AUTH_ONCE=true` skips re-login. This is fine while the old machine is off or gone.
- **If both run,** Tailscale's docs name this case: devices restored from "a backup of one device" or a cloned file system share an address. The admin console shows a **Duplicate node key** badge, and "the Tailscale files will need to be removed from one of the two" ([multiple-devices-same-100.x-ip-address](https://tailscale.com/docs/reference/troubleshooting/network-configuration/multiple-devices-same-100-x-ip-address)). Tailscale does not describe the runtime behaviour beyond that (**unverified**). Treat restoring the state as moving the node.
- On Linux and Windows, state-file encryption is opt-in from 1.92.5 (`tailscaled --encrypt-state`). It uses the TPM, and "to read or modify the state file, Tailscale has to decrypt it with the exact same TPM device" ([secure-node-state-storage](https://tailscale.com/kb/1596/secure-node-state-storage)). An encrypted state therefore can't be restored on other hardware. The page doesn't mention containers. That the `tailscale/tailscale` image leaves it off is **unverified**; the prototype doesn't pass the flag.
- **Not restoring, re-joining with a new key and `TS_HOSTNAME=rakazo`** while the old node still exists: "the new machine will get a name like `<hostname>-1`". It keeps that name even if the old one is renamed later ([machine-names](https://tailscale.com/docs/concepts/machine-names)).
  - To avoid it, remove the old node in the admin console **before** joining. Whether the name frees immediately on removal is not stated (**unverified**).
  - Or rename afterwards with `tailscale set --hostname=rakazo` or the console. Renaming also changes the MagicDNS name (same page).
  - Either way the Instance URL (`https://rakazo.<tailnet>.ts.net`) depends on getting `rakazo` back (Q5).

## 10. Cross-OS restore

- **Formats are portable.** Custom-format dumps "are designed to be portable across architectures" ([PG16 pg_dump.sgml#L69-L71](https://github.com/postgres/postgres/blob/REL_16_0/doc/src/sgml/ref/pg_dump.sgml#L69-L71)). Copying the raw `pgdata` volume across x86-64 and arm64 is not covered by that promise, so use dumps.
- **Docker Desktop volumes live in its Linux VM's disk image.** "Docker Desktop stores Linux containers and images in a single, large 'disk image' file" ([D/…/macfaqs.md#L30](https://github.com/docker/docs/blob/b34003b10479ee377b6e5ce81ad5c6e67e5087b9/content/manuals/desktop/troubleshoot-and-support/faqs/macfaqs.md#L30)). Settings call it "the Linux volume where containers and images are stored" ([D/…/settings.md#L69](https://github.com/docker/docs/blob/b34003b10479ee377b6e5ce81ad5c6e67e5087b9/content/manuals/desktop/settings-and-maintenance/settings.md#L69)). The docs don't name the filesystem for named volumes; ext4 and case sensitivity are **unverified**. Docker Desktop wasn't running here, and the check is `docker run --rm -v t:/v busybox sh -c 'touch /v/a /v/A; ls /v; stat -f /v'`.
- **Keep extraction inside a Linux container.** Docker warns "Mac file systems are case-insensitive while Linux is case-sensitive" ([settings.md#L103](https://github.com/docker/docs/blob/b34003b10479ee377b6e5ce81ad5c6e67e5087b9/content/manuals/desktop/settings-and-maintenance/settings.md#L103)). The tarball is one opaque file on the host, so this only bites if an archive is unpacked onto APFS/NTFS. On Windows, setup runs inside the WSL2 distro on ext4 (`research/bun-binary`).
- **Ownership:** archive and extract with numeric ids. Every `up` runs `data-init` `chown -R 1000:1000 /data` before the supervisor, api and worker start ([R/infra/compose/docker-compose.images.yml#L298-L305](https://github.com/elie222/rakazo/blob/v0.4.0/infra/compose/docker-compose.images.yml#L298-L305)). It heals any owner drift; mode bits come from tar. Computers run as `1000:1000` ([computer-spec.ts#L66-L68](https://github.com/elie222/rakazo/blob/v0.4.0/infra/sandboxes/supervisor/src/computer-spec.ts#L66-L68)), and the api image runs as `USER node` ([R/infra/compose/Dockerfile#L45](https://github.com/elie222/rakazo/blob/v0.4.0/infra/compose/Dockerfile#L45)).
- **Symlinks** inside homes survive tar between Linux volumes. Rakazo's own restore code also rejects a `data/` that is itself a symlink ([R/scripts/restore.sh#L12-L15](https://github.com/elie222/rakazo/blob/v0.4.0/scripts/restore.sh#L12-L15)).
- No other OS coupling was found. The volume subpath mount needs Engine API 1.45+ on every platform ([computer-spec.ts#L519-L524](https://github.com/elie222/rakazo/blob/v0.4.0/infra/sandboxes/supervisor/src/computer-spec.ts#L519-L524)).

## 11. Archiving through Docker

- **Volume:** Docker's documented pattern is a throwaway container that mounts the volume and a host directory and runs `tar` ([D/content/manuals/engine/storage/volumes.md#L726-L767](https://github.com/docker/docs/blob/b34003b10479ee377b6e5ce81ad5c6e67e5087b9/content/manuals/engine/storage/volumes.md#L726-L767)). Streaming over stdout avoids a host bind mount, which matters on Desktop. For example: `docker run --rm -v rakazo-stack_appdata:/data:ro <image> tar -C /data -czf - --numeric-owner . > appdata.tgz`, and `docker run --rm -i -v <vol>:/data <image> tar -C /data -xzf - --numeric-owner` to restore.
- **Run it as root** (the image default) so mode-600 files are readable, which is why upstream avoids `exec api` (Q1).
- **Prefer GNU tar**, for its "file changed" exit code 1 that upstream relies on. The Debian-based `postgres:16` image is already pulled and has it. Busybox tar's exit codes and long-name handling weren't checked (**unverified**).
- **DB:** `docker compose exec -T postgres sh -c 'pg_dump -Fc -U "$POSTGRES_USER" "$POSTGRES_DB"' > rakazo.dump`. To restore, pipe into `exec -T postgres sh -c 'pg_restore … -d "$POSTGRES_DB"'`, exactly as upstream does (Q1). `$POSTGRES_USER` expands inside the container, so the setup program never needs the password.
- **TTY pitfall:** `compose exec` "allocates a TTY by default" ([C/docs/reference/compose_exec.md#L6-L13](https://github.com/docker/compose/blob/v5.7.0/docs/reference/compose_exec.md#L6-L13)). With a TTY, "the stream is not multiplexed … simply the raw data from the process PTY" ([M/api/swagger.yaml#L9147-L9152](https://github.com/moby/moby/blob/8bffe38a06eb9917b636008d9a31c5bea9531230/api/swagger.yaml#L9147-L9152)). stderr then mixes into the dump and the terminal line discipline can rewrite bytes. Compose v5.7.0 defaults `-T` to on only when stdout isn't a terminal ([C/cmd/compose/exec.go#L86](https://github.com/docker/compose/blob/v5.7.0/cmd/compose/exec.go#L86)). A restore with stdin from a file and stdout on a terminal would still get a TTY. Always pass `-T`.
- **Other pitfalls:**
  - **Errors:** check the exit codes of every pipe stage; upstream uses `PIPESTATUS`. A failed dump leaves a partial file that looks valid until restored, so verify with `pg_restore --list` and `tar -tzf` as upstream does.
  - **Large output:** stream to disk rather than buffering in the Bun process.
  - **Privacy:** write output files `0600`, because homes are plaintext (Q2).
